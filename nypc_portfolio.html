NYPC 대회 진행 과정

NYPC 2026은 Qualification Round와 Final Round로 구성된다. Master Track은 AI 1:1 대결 문제가 출제되며, 참가자는 주어진 게임 환경에서 승리할 수 있는 AI 코드를 작성한다. 예선에서 작성한 코드는 본선 문제와 기본 틀을 공유하기 때문에, 단순 풀이보다 전략 설계와 로그 기반 개선이 중요하다.

STEP 1

참가 신청과 팀 구성

NYPC 홈페이지에서 참가 신청을 하고 팀을 구성한다. Master Track은 팀 단위로 AI 코드를 개발하고 제출한다.

STEP 2

연습문제와 환경 확인

로컬 CLI 도구, 리플레이 로그, 명령 형식을 확인한다. 인터랙티브 게임은 좋은 전략보다 먼저 유효한 명령을 내는 안정성이 중요하다.

STEP 3

Qualification Round

예선 기간 동안 코드를 계속 제출하고, 여러 상대 유형과 맵에 대해 승률을 비교한다. 대표 답안 선택과 리플레이 제출도 포함된다.

STEP 4

Final Round

상위 팀은 오프라인 결선에 진출한다. 본선 문제는 미리 공개되지 않지만 예선 코드의 구조와 전략을 일부 재사용할 수 있다.

우리 팀의 진행 과정

처음부터 압박 전략이 완성되어 있던 것은 아니다. 경제를 째는 버전, 중앙을 과하게 보는 버전, 병력을 계속 뽑는 버전, 공격 후 쉬는 버전을 모두 겪었다. 최종적으로는 “상대 경제를 먼저 흔들고, 그 사이에 본부와 기지를 자산화한다”는 방향이 가장 잘 맞았다.

1단계

규칙 해석: 금화보다 자산이 중요하다

초반에는 금화를 많이 들고 있는 것보다 기지, 본부 레벨, 전사 체력으로 바꾸는 것이 중요하다고 판단했다. 그래서 단순 현금 보유량이 아니라 수입 건물 수와 본부 업그레이드를 핵심 지표로 봤다.

2단계

오프닝: 3기지 9병력

초반 목표를 3기지와 9병력으로 고정했다. 9명을 모두 공격에 쓰지 않고, 5명만 상대 거점으로 보내고 나머지는 본부와 기지 수입을 유지하도록 했다.

3단계

로그 분석: 병사가 쉬거나 왕복하는 문제 발견

리플레이를 보니 병사가 본부와 기지를 왔다 갔다 하거나, 공격조가 상대 기지 하나를 친 뒤 멈추는 문제가 있었다. 이때부터 병사 역할을 명시적으로 분리하기 시작했다.

4단계

압박 전략 강화

상대가 안전하게 운영하는 경우가 많았기 때문에, 우리 쪽은 조금 더 경제적으로 째면서도 상대 기지를 먼저 부수는 방향으로 조정했다. 압박이 들어가면 상대의 수입과 병력 생산 타이밍이 흔들렸다.

5단계

최종 정리: 공격조와 확장조 분리

가장 마지막까지 남은 문제는 공격부대가 성공했는데 운영이 따라오지 못하는 것이었다. 그래서 공격조는 계속 상대 거점을 찾고, 운영조는 본부 업그레이드와 추가 기지 확보를 보도록 나눴다.

최종 코드 딥다이브

최종 코드는 “하나의 거대한 if문”처럼 보이지만 실제로는 역할별 레이어를 쌓은 구조다. 입력을 내부 상태로 재현하고, 경로를 미리 계산하고, 오프닝/경제/전투/방어/최종 필터가 순서대로 명령을 만든다. 아래는 코드에서 왜 이런 구조를 선택했는지에 대한 분석이다.

데이터 모델: Warrior, Building, GameState, Actions

왜 클래스로 상태를 직접 재현했나

이 게임은 매 턴 명령을 내리는 인터랙티브 구조라서, 현재 병사 위치와 건물 상태를 내부에서 보수적으로 추적해야 한다. 금화, 이동 중인 병사, 건물 레벨을 잘못 기억하면 유효하지 않은 명령을 내서 바로 패배할 수 있다. 

class Warrior:
    id: WarriorId
    region: int
    hp: int
    state: WState = WState.STATIONARY
    target: int = 0

class Building:
    region: int
    side: Side
    type: BType
    level: int = 1
    hp: int = 10

class Actions:
    train_n: int = 0
    moves: list[tuple[WarriorId, int]]
    upgrades: list[int]
  • Warrior는 병사의 현재 위치, 체력, 이동 여부를 담는다. 이동 중인 병사에게 다시 MOVE를 내지 않기 위해 필요했다.
  • Building은 본부와 기지의 레벨, 체력, 노동 수용량을 계산한다. 업그레이드 기대값 판단의 기준이다.
  • Actions는 한 턴에 낼 명령을 모아두는 버퍼다. 여러 레이어가 명령을 추가한 뒤 마지막에 검증한다.
경로 계산: Paths, next_step, path

왜 최단 경로를 미리 계산했나

전장은 매번 다르게 생성되고, 이동 비용과 도착 시간은 전략 판단의 핵심이다. 공격 목표까지 몇 턴 걸리는지, 기지를 짓기 위해 어느 병사를 보내야 하는지를 빠르게 판단하기 위해 모든 구역 간 최단거리를 미리 계산했다. 

def path(P: Paths, u: int, v: int) -> list[int]:
    if P.nxt[u][v] == -1:
        return []
    out = [u]
    while u != v:
        u = P.nxt[u][v]
        out.append(u)
    return out
  • 기지 후보를 고를 때 P.dist[M.my_hq][r]로 가까운 거점을 빠르게 정렬했다.
  • 공격 목표를 고를 때 travel 값을 계산해 너무 먼 거점은 점수를 낮췄다.
  • 병력이 따로따로 도착해 죽는 문제를 줄이기 위해 도착 턴 차이를 보는 데 사용했다.
오프닝: _opening_plan, _run_opening

왜 오프닝을 고정했나

초반은 선택지가 많아 보이지만 실제로는 실수 비용이 크다. 기지 없이 병력만 뽑으면 수입이 부족하고, 중앙만 보다가 병력이 끊기면 손해가 커진다. 그래서 초반에는 자유도를 줄이고 3기지와 9병력까지의 길을 고정했다. 

def _opening_plan(M, P):
    center = M.N // 2
    near = sorted([r for r in M.strongholds if r != center],
                  key=lambda r: (P.dist[M.my_hq][r], r))
    first = near[0]
    second = near[1]
    return first, center, second
  • first: 본부에서 가까운 기지라 안정적인 첫 수입원이다.
  • center: 전장 중앙은 이후 압박과 방어의 기준점이다.
  • second: 3기지 운영을 완성해 9병력 러시의 생산 기반을 만든다.
기지 계획: _base_plan, _expansion_goal, _assign_base_builder

왜 맵 크기에 따라 확장 목표를 다르게 했나

작은 맵에서는 기지를 많이 늘리기 전에 전투가 먼저 일어나고, 큰 맵에서는 기지를 적게 먹으면 후반 수입 차이가 크게 벌어진다. 그래서 맵의 전체 거리와 구역 수에 따라 목표 기지 수를 다르게 잡았다. 

if M.N >= 95 or total >= 12:
    if turn < 35: return 5
    if turn < 70: return 8
    if turn < 115: return 10

if M.N >= 60 or total >= 8:
    if turn < 40: return 3
    if turn < 90: return 5
  • 큰 맵은 이동 시간이 길기 때문에 미리 기지 후보로 일꾼을 보내야 한다.
  • 작은 맵은 너무 욕심내면 바로 공격에 맞기 때문에 목표를 낮춘다.
  • _planned_base_count는 이미 이동 중인 일꾼까지 계산해 중복 확장을 줄인다.
노동 보호: _protected_worker_ids, _enforce_income_floor

왜 병사를 마음대로 빼지 못하게 했나

이 게임에서 병사는 전투 유닛이면서 동시에 수입을 만드는 노동자다. 기지에 병사가 없으면 건물이 있어도 경제력이 줄어든다. 초반 로그에서 공격하러 간 병사 때문에 기지가 놀고 있는 문제가 있었고, 그래서 경제 건물의 최소 노동자를 보호했다. 

def _enforce_income_floor(S, M, P, a, turn=1):
    upkeep = UPKEEP_PER_WARRIOR * len(_mine(S, M))
    labor_ids = _protected_worker_ids(S, M, P)
    moving.difference_update(labor_ids - forced_attack_ids)
    if income(moving) >= upkeep:
        return a
  • 공격 가치가 낮은 이동보다 수입 유지가 우선인 상황을 걸러냈다.
  • 단, 강제 공격 타이밍에는 일부 병사를 빼도록 예외를 두었다.
  • 이 로직은 “쓸데없는 이동보다 가만히 있는 게 낫다”는 피드백에서 나온 핵심 장치다.
본부 업그레이드: _hq_upgrade_pressure, _upgrade_hq_when_rich

왜 본부 업그레이드를 별도 압력 지표로 봤나

본부 레벨은 단순 체력 증가가 아니라 전사 체력, 포탑, 훈련량, 노동 수용량을 함께 올린다. 그래서 “금화가 많으면 훈련”이 아니라, 일정 경제 기반이 생기면 본부 레벨을 올리는 것이 장기 기대값이 컸다. 

if bases >= hq.level + 1:
    pressure += 2
if units >= current_slots:
    pressure += 2
if bases >= 3 and hq.level == 1:
    pressure += 2
  • 기지가 충분한데 본부가 낮으면 노동 수용량과 병사 질이 막힌다.
  • 본부 업그레이드 타이밍을 놓치면 후반 판정에서 손해를 봤다.
  • 그래서 reserve로 업그레이드 비용을 먼저 남겨두고 훈련을 제한했다.
전투 계산: _simulate_siege, _eval_target_with_group

왜 단순 병력 수가 아니라 모의 전투를 넣었나

처음에는 “우리 병력이 더 많으면 공격”처럼 판단했지만, 포탑과 체력 차이 때문에 실제로는 한 명씩 죽는 경우가 많았다. 그래서 건물 체력, 포탑 공격, 수비 병력, 공격 병력의 체력을 넣어 보수적인 공성 시뮬레이션을 만들었다. 

score = sim["damage"] * 23
score -= sim["lost"] * 34
score -= travel * 5
if sim["destroyed"]:
    score += 330
  • 공격 성공 확률뿐 아니라 병력 손실 비용을 점수에 반영했다.
  • 멀리 있는 목표는 이동 시간 때문에 점수를 낮췄다.
  • 상대 기지를 부수면 미래 수입을 차단하므로 추가 점수를 줬다.
공격조 상태: _combat_state, _plan_state

왜 공격부대를 상태로 묶었나

병사를 매 턴 새로 고르면 가까운 병사 한두 명만 계속 앞으로 가는 “찔끔 공격”이 생긴다. 그래서 공격에 참여한 병사 ID를 상태로 저장하고, 모일 때는 모이고 공격할 때는 함께 움직이도록 했다. 

_combat_state = {
    "wave_ids": set(),
    "wave_target": None,
    "wave_start_turn": -999,
    "last_wave_end": -999,
    "cooldown": 0,
}
  • wave_ids는 현재 공격부대의 멤버를 고정한다.
  • wave_target은 목표가 흔들리지 않도록 잡아둔다.
  • cooldown은 한 번 실패한 공격을 바로 반복하지 않게 한다.
러시 체인: raider_ids, chain_target

왜 5마리만 따로 빼서 운영했나

가장 잘 통했던 전략은 모든 병력을 몰아넣는 올인이 아니라, 5마리만 계속 상대 경제를 흔드는 압박이었다. 이 5마리는 일반 노동/확장 로직에 섞이면 멈추기 때문에, 별도 ID 목록으로 관리했다. 

_v50_state = {
    "target": None,
    "done": False,
    "raider_ids": set(),
    "chain_target": None,
}
  • raider_ids는 공격조 5명을 고정해 일반 운영에서 빠지게 한다.
  • chain_target은 첫 기지를 부순 뒤 다음 상대 기지를 계속 찾게 한다.
  • 상대 본부가 비거나 후반 킬각이 보이면 HQ 압박으로 전환한다.
최종 검증: _v27_sanitize_actions

왜 마지막 필터가 꼭 필요했나

여러 전략 레이어가 같은 턴에 명령을 추가하면 중복 이동, 이미 이동 중인 병사 재이동, 잘못된 업그레이드가 생길 수 있다. 대회에서는 이런 명령 하나가 WA로 이어질 수 있어서, 최종 출력 직전에 한 번 더 정리했다. 

if w is None or w.id.side is not M.my_side:
    continue
if w.state is not WState.STATIONARY:
    continue
if w.region == tgt:
    continue
  • 이미 이동 중인 병사에게 MOVE를 내지 않는다.
  • 같은 병사에게 여러 목적지가 잡히면 마지막 판단을 우선한다.
  • 상대 기지 앞에 아군 기지를 짓는 잘못된 전진기지 명령을 차단했다.

의사결정 흐름

최종 decide() 함수는 매 턴 같은 순서로 판단한다. 중요한 점은 공격, 경제, 방어가 동시에 존재하지만 우선순위를 정해 서로 충돌하지 않게 했다는 것이다.

1. 현재 위험도 측정

상대 병력이 우리 본부 쪽으로 얼마나 들어왔는지, 중앙이나 앞기지에 압박이 있는지 계산한다. 위험도가 높으면 확장보다 생존을 우선한다.

2. 오프닝 수행

초반에는 3기지와 9병력이라는 정해진 루틴을 먼저 수행한다. 이 구간은 변수가 적을수록 안정적이었다.

3. 5마리 공격조 운영

러시가 시작되면 공격조는 일반 운영과 분리된다. 상대 기지 하나를 부순 뒤에도 쉬지 않고 다음 기지를 찾도록 만들었다.

4. 경제와 본부 업그레이드

공격조가 상대를 흔드는 동안 운영조는 기지를 늘리고 본부를 올린다. 돈을 쌓는 것이 아니라 자산으로 바꾸는 단계다.

5. 훈련 제한

무조건 병력을 많이 뽑으면 수입과 업그레이드가 늦어진다. 그래서 공격조 이후에는 필요한 만큼만 보충하고 나머지는 확장과 본부 업그레이드에 쓴다.

6. 최종 명령 정리

여러 레이어가 만든 명령을 마지막 필터에서 정리한다. 이 과정이 없으면 전략이 좋아도 중복 명령이나 불가능한 명령으로 무너질 수 있다.

트러블슈팅과 해결 과정

실제 개선은 대부분 로그를 보고 이루어졌다. “전략이 틀렸다”보다 “코드가 의도한 전략을 실행하지 못했다”가 더 큰 문제였다. 아래는 우리가 겪은 대표적인 문제와 해결 방식이다.

문제 1

러시가 한 번 치고 멈춤

처음에는 공격 목표가 사라지면 병사들이 일반 운영에 섞였다. raider_ids와 chain_target을 두어 공격조가 다음 상대 기지를 계속 찾게 했다.

문제 2

병사가 본부와 기지를 왕복

노동, 방어, 공격 명령이 동시에 들어가며 병사가 왔다 갔다 했다. 최종 이동 필터와 노동자 보호 로직으로 의미 없는 이동을 줄였다.

문제 3

상대 기지 앞에 기지를 지음

전진요새 로직이 확장과 압박을 혼동했다. 상대 기지 근처의 비본부 업그레이드를 차단하고, 전진기지 레이어를 제거했다.

문제 4

골드가 병력으로 새어 나감

러시 이후에도 훈련 cap이 커져서 본부 업그레이드와 기지 건설이 늦어졌다. reserve를 두고, 5기지 전에는 추가 훈련을 제한했다.

문제 5

기지가 있어도 수입이 부족함

기지에 병사가 없으면 노동 수입이 나오지 않는다. 각 경제 건물마다 최소 노동자를 남기는 기준을 세워 수입 바닥선을 유지했다.

문제 6

200턴 판정 대응 부족

후반에는 새 기지를 짓는 가치가 낮아진다. 145턴 이후에는 확장보다 본부 체력, 본부 레벨, 마지막 압박을 더 중요하게 보도록 조정했다.

왜 압박 전략이 잘 통했나

많은 상대는 안전한 명령, 보수적인 확장, 무난한 방어를 우선했다. 그래서 우리가 먼저 상대 기지를 치면 상대는 확장과 방어를 동시에 처리해야 했고, 그 사이 우리 본부 업그레이드와 수입 기반이 따라붙을 수 있었다.

최종 전략 레이어

Opening3기지와 9병력까지 안정적으로 도달
Raid5명 공격조가 상대 기지를 연속 타격
Economy기지 수입과 본부 업그레이드로 자산화
Defense본부 직접 위협만 최소 대응
Endgame200턴 판정에서 본부와 전투 점수 관리
“돈을 많이 번다는 것은 금화를 쌓는 것이 아니라, 본부 레벨과 기지 수입과 병력의 질로 바꾸는 것이다.”

배운 점

이번 프로젝트에서 가장 크게 배운 것은 로그 기반 개선의 중요성이다. 머릿속 전략은 그럴듯해도, 실제 리플레이에서는 병사가 쉬거나, 잘못된 기지를 짓거나, 중요한 순간에 돈을 잘못 쓰는 일이 반복됐다.

Lesson

역할 분리가 전략을 코드로 만든다

공격조, 노동자, 확장 일꾼, 본부 수비를 분리하지 않으면 모든 병력이 애매하게 움직인다.

Lesson

휴리스틱의 핵심은 예산 배분이다

훈련, 이동, 건설, 본부 업그레이드 중 무엇이 지금 가장 큰 기대값인지 매 턴 비교해야 한다.

Lesson

마지막 필터가 승률을 지킨다

전략이 좋아도 불가능한 명령 하나면 끝난다. 출력 직전 검증은 전략만큼 중요했다.
